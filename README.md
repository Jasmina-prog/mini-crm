# Мини-CRM «Объекты и задачи»

Постановщик заводит объекты и задачи, назначает исполнителей и проверяет работу. Исполнитель видит только свои задачи и двигает их по статусам. Все правила доступа проверяются в базе данных, а не только в интерфейсе.

## Стек

React 19 + TypeScript + Vite, UI на Mantine. Бэкенд — Supabase: Postgres, Auth, Row Level Security. Хостинг — Vercel.

```
supabase/migrations/   схема → функции и триггеры → RLS и права (выполнять по порядку)
supabase/tests/        SQL-тесты безопасности на локальном Postgres
scripts/seed.ts        демо-пользователи, объекты, задачи в разных статусах
scripts/security-check.ts  попытки обойти защиту через API с публичным ключом
src/                   фронтенд
```

## Запуск

1. Создайте проект на [supabase.com](https://supabase.com) (хватит бесплатного тарифа).
2. Примените миграции: в **SQL Editor** по очереди выполните три файла из `supabase/migrations/`. Можно и через `psql` по строке подключения из Project Settings → Database:
   ```bash
   for f in supabase/migrations/*.sql; do psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f "$f"; done
   ```
3. Закройте регистрацию: **Authentication → Sign In / Providers → Allow new users to sign up = off**.
4. Заполните переменные окружения:
   ```bash
   cp .env.example .env.local   # URL, publishable/anon-ключ, secret-ключ (только для seed), пароль демо-пользователей
   ```
5. Установите зависимости, создайте демо-данные и запустите:
   ```bash
   npm install
   npm run seed            # повторно: npm run seed -- --reset
   npm run dev
   ```

### Деплой на Vercel

Импортируйте репозиторий (Framework: Vite) и задайте **только** `VITE_SUPABASE_URL` и `VITE_SUPABASE_ANON_KEY`. Секретный ключ на хостинг не нужен. `vercel.json` перенаправляет все пути на `index.html`, поэтому прямые ссылки вида `/tasks/…` открываются корректно.

## Как устроена защита

- **RLS на всех таблицах.**
  - Исполнитель читает только задачи, где он назначен.
  - Объекты он видит только те, где у него есть задачи, а историю — только по своим задачам.
  - Создавать, изменять и удалять объекты и задачи может только постановщик.
- **Права по колонкам.**
  - Через API можно записать только `name`/`address` объекта и `object_id`/`title`/`description`/`assignee_id` задачи.
  - `status`, `author_id` и `created_at` недоступны для записи. Автор и время создания проставляются триггером.
- **Смена статуса** возможна только через функцию `change_task_status`. Она:
  - блокирует строку задачи;
  - проверяет роль, исполнителя и допустимость перехода;
  - при возврате на доработку требует комментарий;
  - пишет запись в историю.

  Прямой `UPDATE status` отклоняется триггером для всех, в том числе для постановщика.
- **История неизменяема.**
  - Прав на INSERT/UPDATE/DELETE нет ни у кого, включая `service_role`. Записи создают только триггер и функция смены статуса.
  - Отдельный триггер запрещает UPDATE и DELETE даже владельцу таблицы.
  - Записи удаляются только каскадом вместе с самой задачей.
- **Роли.**
  - Роль хранится в `profiles`. Новый пользователь по умолчанию получает роль «исполнитель».
  - Роль выставляет администратор: скрипт `seed` или SQL. Таблица `profiles` через API доступна только для чтения.
- **Ключи.**
  - Во фронтенде используется только публичный ключ. `src/lib/supabase.ts` откажется запускаться с секретным ключом.
  - Секретный ключ лежит только в `.env.local`, который не попадает в git, и нужен только скрипту `seed`.
