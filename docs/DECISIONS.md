# Решения и допущения

## Роли и доступ

1. **Одна роль на пользователя.**
   - Роль хранится в таблице профилей. Её выставляет администратор: скрипт `seed` (через секретный ключ) или SQL-запрос.
   - Новый пользователь по умолчанию получает роль «исполнитель». Через API пользователь роль не изменит.
2. **Исполнитель видит объект, только если в нём есть его задача.**
   - В карточке такого объекта видны только его собственные задачи.
   - Если задачу переназначить на другого исполнителя, прежний исполнитель сразу теряет доступ к ней и к её истории.
3. **Имена пользователей видны всем вошедшим.** Без этого нельзя показать автора, исполнителя и участников истории. Таблица профилей доступна только для чтения.
4. **Все постановщики равноправны.** Любой из них может принять или вернуть любую задачу, не только свою.

## Задачи и статусы

5. **Статус меняется только через действия.** Это функция в базе, которая проверяет роль, исполнителя и допустимость перехода. Напрямую записать статус нельзя никому, включая постановщика.
6. **Исполнитель обязателен** при создании задачи, и это должен быть пользователь с ролью «исполнитель». Назначить задачу постановщику нельзя.
7. **Постановщик может редактировать поля задачи в любом статусе**, в том числе после принятия: название, описание, объект, исполнителя. Статус при этом не меняется. Исполнитель поля не редактирует, потому что по ТЗ у него есть только действия со статусом.
8. **Комментарий.**
   - При возврате на доработку комментарий обязателен.
   - При остальных переходах его можно оставить по желанию, он тоже попадает в историю.
9. **Создание задачи тоже пишется в историю** (переход «— → Новая»). Автор и время создания проставляет база, подделать их нельзя.

## Удаление

10. **Удаление задачи удаляет и её историю.**
    - Отдельно удалить или изменить историю нельзя: это запрещено правами и триггером, даже для служебного ключа.
    - История живёт, пока существует задача. Если нужно хранить её вечно, следующий шаг — «мягкое» удаление (архив) вместо физического.
11. **Объект с задачами удалить нельзя.** Сначала нужно удалить или перенести его задачи. Интерфейс подскажет это сообщением.

## Интерфейс

12. **Кнопки действий рассчитываются в интерфейсе только для отображения.** Решение о том, разрешено ли действие, всегда принимает база.
13. **Раздел «Мои задачи» у постановщика называется «Все задачи».** По умолчанию в нём открыт фильтр «На проверке», чтобы было видно, что ждёт решения.
14. **Регистрация закрыта** в настройках Supabase Auth. Пользователей создаёт администратор.

## Что не сделано

- Нет управления пользователями в интерфейсе (создание, смена роли, сброс пароля). Сейчас это делается скриптом или в панели Supabase.
- Нет обновления в реальном времени: чтобы увидеть изменения другого пользователя, нужно обновить страницу.
- Нет поиска, пагинации, сроков, приоритетов и вложений.
- В истории фиксируются только смены статуса, а не правки полей (так в ТЗ).
- Нет автоматических E2E-тестов интерфейса. Защита покрыта SQL-тестами (`npm run test:db`) и проверкой через API (`npm run security-check`).
- Сборка не разбита на части (около 225 КБ в gzip). Для такого объёма это не критично.
